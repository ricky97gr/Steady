# 优化路线图

> 依据当前代码现状核对（2026-08-20）后整理。已实现的能力标记 ✅，待办标记 🚧。

## 当前阶段判断

项目已过了"搭框架"阶段，下一步重点应从继续堆页面和新策略，转向：

> 可观测通知 → 数据与交易可靠性 → 回测可信度校准 → 策略与风控迭代

## 部署后第一项：数据源稳定化（Tushare 主源 + akshare 兜底）🚧

> 决策背景（2026-08-21）：稳定优先。akshare 刮公共网页，随东财/新浪改版漂移；Tushare Pro 为 token + 官方 API，契约更稳。免费档（120 积分，50 次/分钟）够日线增量同步，分钟线需高积分单独开权限（不阻塞本项）。

### 目标

- 日线 / 估值 / 财务：**Tushare 主源 → akshare 兜底**，主源失败自动降级，不中断
- 盘中实时快照：**保持 akshare**（东财一次拉全市场，Tushare 实时也要积分）
- 15-min 历史回测：暂不做（免费源深度不够，待冲积分再议）

### 范围

- `collector/app/config.py`：`TUSHARE_TOKEN` 接入 + 主/备源开关（默认 Tushare）
- `collectors/daily.py`：Tushare `daily` 实现，失败降级 akshare
- `collectors/valuation.py` / `finance.py`：评估是否一并切换（积分门槛先查证）
- `collectors/stock.py` / `calendar.py`：股票列表与日历可切 Tushare（120 积分档查证）
- 现有 `TUSHARE_TOKEN` 已在 `.env.example` / 后端配置中占位，补采集侧接入即可

### 验收标准

1. Tushare 主源日线同步成功，数据与 akshare 对照一致
2. 模拟 Tushare 失败 → 自动降级 akshare，任务不失败、无重复数据
3. 降级链路有日志（`source=akshare`），可观测

## 优先级一：完成飞书通知（Issue #5）🚧

### 阶段一：统一通知基础设施

新增轻量通知模块：

```text
quant-engine/app/notify.py
backend/pkg/notify/notify.go
```

支持：

- `FEISHU_NOTIFY_ENABLED`
- `FEISHU_WEBHOOK_URL`
- 请求超时
- 有限重试
- 推送失败只记录日志，不阻塞主业务
- Webhook 地址脱敏日志

不单独拆通知微服务，保持现有架构（模块间仍通过 DB/定时任务协作）。

### 阶段二：接入关键任务

1. **策略信号生成**
   - 交易日期
   - 买入/卖出/持有数量
   - Top N 信号
   - 评分和原因摘要

2. **自动交易**（backend `ExecuteDay` 的 `ExecResult` 已含买/卖/拒单计数，直接透传）
   - 买入、卖出、拒绝数量
   - 幂等跳过原因
   - 失败订单摘要

3. **净值快照**（backend `NavResult` 已含 nav，补齐累计收益/回撤）
   - 当日净值
   - 累计收益
   - 持仓市值
   - 与基准收益对比

4. **回测完成**（`backtest_result` 已含指标）
   - 总收益
   - 年化收益
   - 最大回撤
   - Sharpe

### 阶段三：补齐日报

当前 `quant-engine/app/tasks.py` 的 `job_daily_report` 仍是占位（仅打日志）。应汇总并推送：

- 当日行情同步结果
- 策略信号
- 自动交易结果
- 账户净值
- 回测任务状态

## 优先级二：数据与交易可靠性

### 数据质量检查 🚧

已有基础 ✅：`market_ready` 检查（股票池当日 bar 覆盖率 ≥ 90%，不足则跳过因子计算）。

待补齐：

- 缺失交易日检查
- 重复数据检查
- 价格异常检查
- 估值/财务数据是否过期
- 指数基准是否存在
- **检查结果记录到表并推送飞书**（当前只打日志）

### 交易一致性校验 🚧

现状 ✅：`ExecuteDay` 在单事务内用内存 `Ledger` 演化，cash/持仓/净值天然一致、幂等（净值已存在则跳过）。

待补齐：独立的**每日对账校验**作为防御，检查：

```text
现金余额 + 持仓数量 × 最新价格 = 账户总资产
```

同时校验：

- 订单和成交数量一致
- 撤单后状态正确
- T+1 可卖数量正确
- 净值快照幂等
- 自动交易没有重复执行

发现偏差直接推送飞书告警。

## 优先级三：回测可信度校准

### 现状（规则已全部实现 ✅，无需从零补）

- 分板块涨跌停（主板 10% / ST 5% / 创业板 20% / 科创板 20% / 北交所 30%）— `broker.py`
- 印花税（万5，仅卖出）、佣金（万2.5、最低 5 元）、滑点 0.1% — `broker.py`
- T+1 冻结/解冻、100 股整手、加权平均成本 — `portfolio.py` + `engine.py`
- 停牌/数据缺失跳过、资金不足逐档减 100 股重试（与 Go 模拟盘一致）
- 沪深300 基准对比 + 超额收益 — `engine._get_benchmark_nav`
- 一致性对照测试已存在：`backend/internal/service/trading_consistency_test.go`、`quant-engine/tests/test_broker_consistency.py`

### 真正要做的 🚧

1. **防未来函数（look-ahead bias）验证** ⭐ 最高优先
   - 风险点：`engine.py` 中信号 T 日生成、**同一日**以 T 日收盘成交（`strategy.run(date)` → `_get_price(signal.code, date)`）。
   - 因子层已用 `announce_date <= trade_date`（财务）与 as-of 窗口（估值）防了部分未来函数 ✅，但行情类因子（MA/MACD）是"收盘算信号、收盘成交"，存在 look-ahead 风险。
   - 验证方案：对比 T 日收盘生成 + T 日成交 vs T+1 成交 两种方式的净值差异；确认是否需要改为 T+1 成交。
2. **信号生成日与成交日错位检查**：信号是 T 日盘中生成还是收盘后生成，成交价取哪一天，需明确并保持一致。
3. **固定 fixture 测试**（覆盖边界场景）：
   - 单只股票
   - 多只股票轮动
   - 涨停无法买入
   - 跌停无法卖出
   - 现金不足
   - T+1 卖出限制
   - 空数据区间
   - 停牌期间持有
4. **回测结果可复现性**：同一参数重复运行，结果一致。

## 优先级四：策略与风控迭代

### 现状 ✅（底层已具备）

- 因子权重存于 `factor_definition` 表，`backtest_service.py` 从 DB 读取——**权重已配置化**
- 策略参数（top_n / max_position_pct）存于 `strategy.params`，`execStrategy` 运行时解析

### 待补齐 🚧

- 因子权重 / 策略参数的**前端可视化配置界面**（当前只能改库）
- 多策略对比（同一区间跑多个策略，并排展示）
- 回测结果对比（历史回测任务横向比较）
- 换手率和交易成本分析
- 行业集中度限制
- 最大持仓比例风控
- 止损/止盈规则

暂不优先加入 AI 或机器学习，避免无法区分模型、数据和交易模拟问题。

## 推荐迭代顺序

```text
Iteration 0：部署上线 + 数据源稳定化
  ├── compose 稳定化（restart/内存限额/端口收敛/备份压缩）✅ 已提交
  ├── 数据源切换（Tushare 主源 + akshare 兜底，含降级测试）
  └── 异地备份（备份拷出 VM 系统盘）

Iteration 1：完成 Issue #5
  ├── 飞书通知模块（Python + Go）
  ├── 信号/交易/净值/回测推送
  └── 实现真正的每日汇总日报

Iteration 2：可靠性与告警
  ├── 数据质量检查（记录 + 推送）
  ├── 交易一致性对账校验
  ├── 任务失败告警
  └── 数据库备份恢复验证

Iteration 3：回测可信度校准
  ├── 防未来函数验证（T 日 vs T+1 成交对比）⭐
  ├── 固定 fixture 边界测试
  ├── 回测与模拟盘规则一致性保持（已有一致性对照测试）
  └── 结果可复现性

Iteration 4：策略与风控
  ├── 多策略对比
  ├── 权重/参数前端配置
  ├── 仓位与行业风控
  └── 风险指标
```
